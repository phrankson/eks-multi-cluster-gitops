# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Multi-cluster GitOps reference implementation for Amazon EKS, using FluxCD (GitOps engine) and Crossplane (infra controller) in a hub/spoke model. There is no build/lint/test toolchain for the repo as a whole — it is a collection of Kubernetes/Kustomize/Helm manifests, shell scripts, and two small sample apps. Work here is almost always: edit YAML manifests, edit the bash automation in `bin/`, or edit one of the two sample apps.

## Architecture (read this before touching manifests)

Hub/spoke model:
- **Management cluster** (`mgmt`) is created once manually via `eksctl` (see `initial-setup/`), then bootstrapped with Flux pointed at the `gitops-system` repo.
- Flux on the management cluster deploys Crossplane, External Secrets Operator, and Sealed Secrets into itself, then reconciles **workload cluster** definitions (Crossplane custom resources) from `repos/gitops-system/clusters-config/`. Crossplane provisions the actual EKS workload clusters from those definitions.
- The management cluster also bootstraps Flux onto each newly provisioned workload cluster.
- Each **workload cluster** then runs its own independent Flux + Crossplane (not shared/central) — this is a deliberate scalability choice, not an oversight. Workload-cluster Flux deploys cluster tooling (AWS Load Balancer Controller, EBS CSI, Karpenter, etc.) and the actual application workloads defined in `gitops-workloads`.
- Secrets are never stored in Git in plaintext. Sealed Secrets encrypts secrets client-side (via `kubeseal`) before commit; the Sealed Secrets keypair itself is predefined (not autogenerated) and stored in AWS Secrets Manager, retrieved into each cluster by External Secrets Operator. This predefined-keypair design exists specifically so new workload clusters can bootstrap Flux via GitOps without manual key exchange.

### The four conceptual Git repos (all vendored under `repos/` in this single repo for demo purposes — treat each as if it were its own repo)

| Path | Real repo name | Owner | Purpose |
|---|---|---|---|
| `repos/gitops-system` | `gitops-system` | Platform team | Manifests for every cluster (mgmt + workload) and every tool installed on them. Flux syncs from here. |
| `repos/apps-manifests/*` | `<app>-manifests` | App team | Kustomize base + overlays for one application's k8s resources and any Crossplane infra it needs (e.g. DynamoDB). |
| `repos/gitops-workloads` | `gitops-workloads` | Governance team | The wiring layer — per-cluster folders specifying which app manifests repos/Flux Kustomizations are deployed to which cluster. |
| `repos/apps/*` | app source | App team | Actual application source code (not manifests) for the two demo apps. |

### `repos/gitops-system` internal layout

- `clusters/<name>/` — Flux entrypoint per cluster (`mgmt` or a workload cluster name). Contains `flux-system/` (gotk-components.yaml, gotk-sync.yaml — **auto-generated by `flux bootstrap`, never hand-edit**) plus the root Kustomization for that cluster.
- `clusters-config/<name>/` — the Crossplane XR definition for provisioning that workload cluster (EKS cluster spec, IAM, External Secrets config, Sealed Secrets, git creds). `clusters-config/kustomization.yaml` is the master list of workload clusters — adding/removing an entry here is what triggers Crossplane to create/delete a cluster.
- `tools/` — core tool installs shared across clusters (Crossplane itself, its AWS/K8s providers, External Secrets, Sealed Secrets, Karpenter, AWS LB Controller, EBS CSI, Kubecost) as Flux `HelmRelease`/`HelmRepository` objects.
- `tools-config/` — IAM roles/policies and config objects (via Crossplane) backing the tools in `tools/`, e.g. `crossplane-eks-composition` (the actual EKS cluster Composition/XRD Crossplane uses), `*-iam` folders.
- `workloads/<cluster>/` — per-cluster references to application manifest repos (Flux `GitRepository` + `Kustomization` + sealed git secret), populated by `add-cluster-app.sh`.
- `template/` directories throughout (`clusters/template`, `clusters-config/template`, `workloads/template`) are the source copied by `bin/add-workload-cluster.sh` when provisioning a new cluster — **edit templates, not a specific cluster's copy, when changing baseline behavior for future clusters.**

### `${ACCOUNT_ID}` / other placeholders

Several manifests contain `${ACCOUNT_ID}` and similar placeholders resolved at apply time via Flux Kustomization `spec.postBuild.substituteFrom`, sourced from a `cluster-info` ConfigMap in `flux-system` populated during initial setup. Don't hardcode account IDs in new manifests — follow this substitution pattern.

## Automation scripts (`bin/`)

Most operate only on **local clones** of `gitops-system` / `gitops-workloads` and never commit or push — caller must `git add/commit/push` afterward. The exception is `remove-workload-cluster.sh`, which commits and pushes both repos itself as part of its teardown flow.

- `add-workload-cluster.sh <gitops-system-path> <cluster-name> [gitops-workloads-path]` — the sole entrypoint for adding a cluster (copies `clusters-config/template`, `clusters/template`, `workloads/template`, replaces the `cluster-name` placeholder, registers it in `clusters-config/kustomization.yaml`). The older `add-cluster.sh` variant has been retired.
- `remove-workload-cluster.sh <gitops-system-path> <gitops-workloads-path> <cluster-name>` — the sole entrypoint for removing a cluster: deregisters the cluster, commits/pushes both repos, forces Flux reconciliation, monitors Crossplane teardown, clears stuck finalizers, cleans local kubeconfig context. Requires `kubectl`, `flux`, `yq`, `git`, `aws` CLI. The older `remove-cluster.sh` variant has been retired.
- `add-cluster-app.sh <gitops_workloads_path> <cluster_name> <app-name> <public_key_pem> <git_creds_template_path> <git_private_key_file> <git_public_key_file> <git_known_hosts> <sealed_secrets_public_pem_file>` — onboards an app onto a cluster: copies the app template into the cluster's workloads folder, seals the git credentials with `kubeseal`, updates `kustomization.yaml`. Assumes an `<app-name>-manifests` repo already exists.
- `remove-cluster-app.sh <gitops_workloads_path> <cluster_name> <app-name>` — removes an app from a cluster's `kustomization.yaml` and deletes its folder.
- `update-cluster-app.sh <gitops_workloads_path> <cluster_name> <app_name> <release_tag>` — bumps the app's `git-repo.yaml` `spec.ref.tag` via `yq`, triggering a Flux-driven redeploy.
- `add-app-cluster-overlay.sh <app_manifests_path> <cluster_name>` — scaffolds a new Kustomize overlay for a cluster inside an app-manifests repo.
- `connect-to-cluster.sh <cluster-name>` — must be run with `source`, not executed — fetches the workload cluster's kubeconfig secret from the mgmt cluster's `flux-system` namespace and exports `KUBECONFIG` in the current shell.

`scenarios.md` has full step-by-step walkthroughs (with example commands) for each of: provisioning a cluster, adding/upgrading/removing an app, connecting to a cluster, upgrading/deleting a cluster — read it before implementing new scenario-level automation.

## Sample applications (`repos/apps/`)

- `product-catalog-api` — Python/Flask (`flask-restx`, gunicorn), has `v1/` and `v2/` variants; `v2` adds Crossplane-provisioned DynamoDB (see its manifests overlay). `python:3.12-slim` base image.
- `product-catalog-fe` — Node/Express frontend (`node:22-slim` base image), calls the API.

These exist purely to demonstrate the GitOps flow end-to-end; changes here should stay minimal/illustrative rather than production-grade.

## Key operational facts worth knowing before editing infra manifests

- Crossplane AWS provider in use is `crossplane-contrib/provider-aws` (`*.aws.crossplane.io` API groups) — this upstream project is **archived**; do not add new resource types against it without checking `docs/knowledge-base.md` (FP-1) for the Upbound family-provider migration status/plan.
- `ControllerConfig` (`pkg.crossplane.io/v1alpha1`) is deprecated/removed upstream — this repo already uses `DeploymentRuntimeConfig` (`pkg.crossplane.io/v1beta1`); don't reintroduce `ControllerConfig`.
- `kubeseal` CLI version must always match the Sealed Secrets Helm chart/controller version pinned in `repos/gitops-system/tools/sealed-secrets/sealed-secrets-release.yaml` — check both together when bumping either.
- `gotk-components.yaml` / `gotk-sync.yaml` under any `flux-system/` dir are generated by `flux bootstrap` — never hand-edit; regenerate via bootstrap instead.
- `docs/knowledge-base.md` tracks component versions, known-deprecated API versions, and open future-work items (FP-1/FP-2/FP-3) — check it before assuming a version or API group is current.
